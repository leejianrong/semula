Raw design conversation that seeded the project. Each section is one prompt/response round.

## Round 1: The core idea

### Prompt

I am building applications that use an OpenAI-compatible endpoint to access an LLM call via API. I am using OpenRouter for this but it's racking up costs. I am thinking of making a service (API server with Go or FastAPI) and having it act as a fake LLM. I am happily using Claude Code and OpenAI Codex, and those subscriptions are generous. I am thinking the API server that I make (acting as a fake LLM service) will allow external users to configure expected requests and corresponding responses that are pre-written by the coding subscription agent. Anything I should look out for, like embedding models etc. or some sort of matching that is not exact matching? By the way, this is meant to be a local tool users can just spin up as a container and have it work.

### Response

Building a local containerized "fake LLM" proxy to leverage your generous coding subscriptions (like Claude Code and OpenAI Codex/ChatGPT Plus tooling) is a clever way to slash development costs. However, moving away from exact matching is **essential** because LLM prompts generated by frameworks, agents, or even different user clicks are rarely character-for-character identical due to dynamic system prompts, timestamps, changing conversation histories, or minor formatting variations.

To make a local Go or FastAPI tool that maps dynamic requests to pre-written or agent-generated responses smoothly, here are the major challenges and architectural patterns to look out for.

#### 1. The matching strategy (beyond exact matching)

Exact string matching will fail 95% of the time in real application use. You need a tiered matching pipeline:

- **Tier 1: Intent and keyword heuristics (fast, local)**
  - Before doing heavy ML matching, parse the incoming JSON payload (`POST /v1/chat/completions`).
  - Extract the *last user message* or designated tags.
  - Look for keyword triggers, route names, or specific regex patterns that your coding agent pre-associated with a mock response.
- **Tier 2: Semantic similarity via local embeddings**
  - Instead of matching text strings, embed the incoming prompt and compare it to the embeddings of your pre-recorded prompts using **cosine similarity**.
  - *Implementation:* you don't need a heavy cloud embedding API. Since this runs locally in a container, you can embed text locally using lightweight models (ONNX runtimes or Go/Python bindings for small models like `all-MiniLM-L6-v2` or `bge-small-en-v1.5`). They run entirely on CPU in milliseconds and need negligible RAM.
  - If the cosine similarity crosses a threshold (e.g. > 0.88), it triggers that mock response.
- **Tier 3: Fallback / "ask the real LLM" switch**
  - If no pre-recorded mock meets the similarity threshold, the proxy shouldn't crash or return a 404. It should have a configurable fallback mode: either route to OpenRouter/Anthropic (at a cost), or intercept the request, prompt your local coding agent subscription to generate a response on the fly, save it to the mock database, and return it.

#### 2. Handling state and conversation history

If your applications involve multi-turn conversations (chatbots or agents), matching *only* the latest user message will cause context confusion.

- **The trap:** if a user says *"Fix this bug"* in two completely different features, a simple semantic match on the last message will pull the wrong mock response.
- **The fix:** the mock database should support **session context / conversation traces**. Either match against the structural hash of the last N messages, or allow the configuration to define a mock as a *sequence* (Turn 1 → Turn 2 → Turn 3) using a state machine.

#### 3. Structural and API compatibility traps

Your fake LLM server must mimic the OpenAI API contract down to the exact data types, or client SDKs will break:

- **Streaming (`stream: true`):** most modern LLM apps and agents stream responses so text appears token-by-token. The server cannot return a single JSON block if `stream: true` is requested. It must chunk the pre-recorded response into Server-Sent Events (SSE) (`data: {"choices": [...]}\n\n`) ending with `data: [DONE]`.
- **Tool / function calling:** if your apps use OpenAI function calling or Anthropic tools, the JSON schema of the tool definitions sent by the app must match what the mock expects, or the mock response must include the correct `tool_calls` payload blocks rather than plain text.

#### 4. Choosing your stack: Go vs. FastAPI

**Go (`net/http`, `fiber`, `gin`)**

- *Pros:* builds into a tiny self-contained binary (< 30MB), uses virtually no RAM, spins up instantly in a Docker container, handles concurrent streaming connections effortlessly.
- *Cons:* integrating embedding models requires CGO or Go-native vector libraries, which makes cross-compilation more tedious.

**FastAPI (Python)**

- *Pros:* Python dominates the AI ecosystem. Libraries like `sentence-transformers`, `faiss`, or `chromadb` make local semantic similarity and vector matching trivial.
- *Cons:* Docker images are heavier (PyTorch/Transformers dependencies), though lightweight ONNX runtimes keep them slim.

#### Suggested architecture for the container tool

1. **The config store:** a local SQLite database or a folder of YAML/JSON files inside the container where users define `[{"triggers": ["embed vector or keywords"], "response": "pre-recorded text or tool call"}]`.
2. **The gateway engine:** a FastAPI or Go server listening on `http://localhost:8080/v1`.
3. **The matcher:** checks exact routes, then falls back to a fast local sentence-transformer embedding lookup.
4. **The streamer:** if matched, loops through the mock response text and emits it chunk-by-chunk via SSE if streaming was requested.

## Round 2: Storage, CLI/MCP, dashboard

### Prompt

SQLite is good. How would I store the prompt and response data if I want logical separation between different projects or just to have some sort of organization? Also interested in this service being able to be configured via CLI or MCP so an external agent can set everything up. Oh, and I am interested in having a dashboard too that humans can use to interact with this app. Thoughts and ideas?

### Response

A local, containerized fake LLM proxy with a dashboard, CLI/MCP agent setup, and logical project separation turns your coding subscriptions into a private, local caching and mock registry engine.

#### 1. SQLite schema for logical separation (projects)

To isolate rules and mocks per project (e.g. `project-alpha`, `mobile-app-api`), use a **foreign-key relationship anchored around a `projects` table**.

```sql
-- Projects table
CREATE TABLE projects (
    id TEXT PRIMARY KEY,          -- e.g., slug like 'auth-service'
    name TEXT NOT NULL,
    description TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- Mocks table
CREATE TABLE mocks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id TEXT NOT NULL,
    trigger_type TEXT NOT NULL,    -- 'exact', 'keyword', 'semantic'
    trigger_pattern TEXT NOT NULL, -- the regex, keywords, or text to embed
    embedding BLOB,                -- optional: serialized vector for local semantic search
    response_body TEXT NOT NULL,   -- the raw OpenAI-compatible JSON or text response
    is_streaming BOOLEAN DEFAULT 0,
    hit_count INTEGER DEFAULT 0,
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);

-- Index for fast lookups by project
CREATE INDEX idx_mocks_project ON mocks(project_id);
```

**Project routing:** apps can pass the project name either via a custom header (`X-Mock-Project: auth-service`) or embedded in the API base URL (`http://localhost:8080/v1/projects/auth-service/chat/completions`).

#### 2. Configuring via CLI and MCP (Model Context Protocol)

Since you want your coding agent (Claude Code, Codex) to dynamically provision and update mocks, an **MCP interface** alongside a CLI is the gold standard.

- **The Python/FastAPI advantage:** Python's ecosystem makes adding an MCP server seamless with **FastMCP**. You can wrap your FastAPI backend or SQLite logic directly into MCP tools so the coding agent can manipulate mocks natively.
- **Exposed MCP tools / CLI commands:**
  - `create_project(name: str)`
  - `upsert_mock(project_id: str, trigger_pattern: str, response: str, match_type: str)`
  - `list_mocks(project_id: str)`
  - `test_match(project_id: str, prompt: str)` (tests which mock would fire for a given prompt)

When configuring a local agent (Claude Desktop or Claude Code), point it at your local script/container via a standard transport:

```json
{
  "mcpServers": {
    "fake-llm-manager": {
      "command": "docker",
      "args": ["exec", "-i", "fake-llm-container", "python", "-m", "mcp_server"]
    }
  }
}
```

While your agent is writing tests or building features against your app, it can write its own mock responses into the proxy on the fly if an API call changes.

#### 3. The human dashboard

Humans want visual validation: which mocks are firing, manual prompt testing, hit counts.

**Keep it lightweight.** Since the app is already a container, don't add a heavy React/Node build toolchain.

**Options**

1. **FastAPI + server-rendered UI (Jinja2 + HTMX + Tailwind via CDN):** the best fit for a local container tool. Zero Node.js build steps, tiny image, snappy reactive single-page dashboard using HTML attributes.
2. **Gradio / Streamlit:** if written in Python, a functional admin dashboard in ~50 lines.
3. **PocketBase or a direct SQLite UI (Datasette):** if using Go, embed a lightweight admin panel or run an open-source SQLite web GUI like *Datasette* or *Adminer* in the compose stack.

**Key dashboard features**

- **Project switcher dropdown:** filter mocks by project.
- **Live request inspector (log stream):** a live table of incoming requests, whether each was a *cache hit* (and which mock matched) or a *cache miss*, with similarity scores.
- **Mock playground:** a sandbox text box to paste a prompt, click "Test Match", and see which mock response it triggers and why.

#### Suggested technology stack blueprint

| Concern | Choice |
| --- | --- |
| Backend | Python + **FastAPI** (fast vector/semantic matching via `sentence-transformers`/`onnxruntime`, easy **FastMCP** integration) |
| Database | **SQLite** (zero config, single file, mount as a Docker volume `-v ./data:/app/data`) |
| Semantic matching | Lightweight local model like `all-MiniLM-L6-v2` on CPU via ONNX (lean container, lookups under ~10ms) |
| UI | HTMX + Tailwind CSS served directly out of FastAPI |

## Round 3: Recording mode

### Prompt

Final idea I have: a "recording" mode. We have the coding agent (Claude Code or Codex on a subscription), the fake LLM that has a recording mode feature, and a client that would typically send API calls to an OpenAI-compatible endpoint. Now, the client would send API calls to our fake LLM OpenAI-compatible endpoint, the coding agent on a subscription will be able to read the request, and then format a response and send it back. So (1) our service is acting as a proxy so I don't have to pay for API costs, and (2) we can record these responses so we can reuse them again and again. Viable?

### Response

**Extremely viable.** This is a local implementation of the **record-replay proxy** pattern (similar to VCR.js or Betamax in testing, but supercharged for AI agents).

Adding a **recording mode** turns your mock server from a tedious manual configuration tool into an automated capture engine.

#### How the recording loop works

1. **Toggle record mode:** flip a switch on the proxy (via the dashboard or an environment variable `PROXY_MODE=record`).
2. **Client sends request:** your application or test suite sends a standard OpenAI-compatible request (`POST /v1/chat/completions`) to the proxy.
3. **Cache miss and interception:** the proxy checks SQLite, sees no matching mock, and realizes it's in record mode.
4. **The subscription agent steps in:**
   - Instead of failing, the proxy packages the incoming prompt/request.
   - It hands it off to your coding agent (Claude Code / Codex via your subscription CLI or API wrapper): *"Generate a valid JSON response that satisfies this request."*
   - Alternatively, if your client app can be temporarily aimed at the real LLM *through* a script that logs both sides, the agent can parse the raw interaction.
5. **Auto-save:** the proxy writes the request pattern (or its embedding vector) and the generated response into SQLite under the active project.
6. **Replay mode:** next run, flip to `PROXY_MODE=replay`. Zero API costs, zero latency, instant responses.

#### Why this architecture shines

- **Zero-maintenance mock writing:** writing JSON responses for complex tool-calling or multi-turn agent interactions by hand is miserable. Letting a coding subscription agent write the mocks while you build features is effortless.
- **Solves the "drift" problem:** if your app's code changes and starts sending slightly different prompts, turn record mode back on for a quick test run. The proxy captures the new variations and layers them into SQLite.
- **Offline development:** code, test, and run integration suites on an airplane or spotty Wi-Fi without burning paid API tokens.

#### Implementation watch-outs for recording mode

- **Timestamps and randomness:** if the response contains dynamic data (current time, generated UUIDs, random tokens), replaying it verbatim might break strict app assertions. Instruct the coding agent during recording to generalize or template dynamic fields where necessary.
- **Streaming chunk capture:** if your app consumes streaming responses (`stream: true`), the recording proxy must capture the incoming SSE chunks sequentially so it can stream them back frame-by-frame during replay.

## Round 4: Matching algorithms and models

### Prompt

What matching algorithms and/or lightweight models (like embedding models or event classifiers/routers) should I be looking into for this app?

### Response

To build a fast, lightweight, low-latency matching engine locally inside a container, you don't need giant deep-learning models or complex vector databases like Pinecone or Milvus. You can achieve near-instant matching (< 10 ms) on a simple CPU using a **hybrid matching strategy** with **pre-quantized ONNX embedding models**.

#### 1. Top recommended lightweight models

To keep the Docker image tiny, boot times under half a second, and RAM around 100–200MB, avoid PyTorch and raw Hugging Face libraries. Run pre-quantized **ONNX models** via ONNX Runtime (Python's `fastembed` library or Go ONNX bindings).

**Dense embedding models**

| Model | Size | Dims | Notes |
| --- | --- | --- | --- |
| `sentence-transformers/all-MiniLM-L6-v2` | ~22MB | 384 | Industry standard for ultra-fast local embeddings. ~5ms on CPU, tiny footprint. Good at general sentence semantics and prompt structure. |
| `BAAI/bge-small-en-v1.5` | ~33MB | 384 | Slightly higher retrieval accuracy than MiniLM, almost as fast and small. |
| `Snowflake/snowflake-arctic-embed-xs` | ~22MB | 384 | Designed for code and retrieval tasks. Good if prompts carry long code snippets or technical schemas. |

#### 2. Matching algorithms and hybrid search strategy

Implement a **multi-tier cascade matcher**. Each API request passes through these tiers in order:

```text
Incoming Request ──► [Tier 1: Exact / Struct Hash] ──(Hit)──► Return Mock
                            │ (Miss)
                            ▼
                     [Tier 2: BM25 Lexical]        ──(Hit)──► Return Mock
                            │ (Miss)
                            ▼
                     [Tier 3: Cosine Vector]       ──(Hit)──► Return Mock
                            │ (Miss)
                            ▼
                     [Fallback: Record Mode / real LLM]
```

**Tier 1: Exact hash and structural matching (0ms)**

- *Algorithm:* SHA-256 or MurmurHash3 on the concatenated message roles and contents.
- *Use case:* the incoming prompt is identical to a recorded one (static system prompts, identical test suite runs), so ML is bypassed entirely.

**Tier 2: Sparse lexical / keyword matching (1–2ms)**

- *Algorithm:* **Okapi BM25** (or `rank_bm25` in Python).
- *Why:* pure semantic vector search often misses exact variable names, function signatures, or technical identifiers (e.g. `getUserById(42)` vs `getUserById(99)`). BM25 handles term-frequency matching.
- *Implementation:* store tokenized BM25 indexes in memory or inside SQLite's FTS5 full-text search engine.

**Tier 3: Dense semantic vector matching (5–10ms)**

- *Algorithm:* **cosine similarity** over dense embeddings.

  $$\text{Cosine Similarity} = \frac{\mathbf{a} \cdot \mathbf{b}}{\Vert\mathbf{a}\Vert \Vert\mathbf{b}\Vert}$$

- *Thresholding:*

  | Score | Action |
  | --- | --- |
  | > 0.90 | High confidence: trigger the mock automatically |
  | 0.75 – 0.89 | Optional "fuzzy match" flag for human review in the dashboard |
  | < 0.75 | Cache miss: trigger record mode |

#### 3. Classifiers and intent routers

If the application triggers vastly different actions (code generation vs. SQL queries vs. JSON summarization), route requests *before* running full prompt comparisons.

- **Lightweight intent router:** `Qdrant/bm42-all-minilm-l6-v2-attentions` (via FastEmbed). Produces sparse lexical vectors for hybrid search and quick document classification without a heavy re-ranker.
- **Zero-shot classifier (optional alternative to embeddings):** train a basic **Naïve Bayes** or **Logistic Regression** classifier (`scikit-learn` with TF-IDF vectors) on recorded prompts. It takes under 1MB of memory and routes requests to project sub-groups or intent categories instantly.

#### 4. Normalization pipeline (the secret sauce)

LLM client frameworks (LangChain, LlamaIndex, OpenAI SDK) alter prompts dynamically before sending. To prevent subtle changes from causing false cache misses, run incoming prompts through a **prompt normalizer** *before* generating embeddings or BM25 tokens:

1. **Strip system headers and dynamic variables:** remove timestamps, generated UUIDs, or absolute directory paths with regex (e.g. replace `/Users/alex/project/src/main.py` with `[FILE_PATH]`).
2. **Role-based token extraction:** instead of embedding the full payload with JSON brackets, extract and format only the conversation tail:

   ```text
   [SYSTEM]: You are a helpful code assistant.
   [USER]: Fix the bug in auth.ts.
   ```

3. **Ignore tool-call metadata differences:** if tool definitions are passed in `tools: [...]`, sort the tools alphabetically by name before computing exact hashes.
